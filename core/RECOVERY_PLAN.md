# Claude Ensemble Recovery Plan

## Purpose

Rebuild Claude Ensemble from the verified foundation commit `5c0bd6ab8af3d111b80f9f9a49b4faa2bf7a2280` after the 2026-09-30 recovery.

The branch `archive/pre-recovery-2026-09-30` preserves the abandoned implementation for reference. It is not a source of wholesale changes.

## Engineering rules

1. Every recovery change starts from the verified `main` baseline.
2. One coherent capability per PR.
3. Real service boundaries are tested end-to-end where applicable.
4. No mocks, fabricated model output, fabricated token counts, or fake success paths in production code.
5. Unit-test doubles are allowed only where they isolate a unit; integration tests must exercise the real boundary.
6. Existing issue acceptance checkboxes are not treated as proof. Behavior must be independently verified.
7. Do not add a second service boundary when the existing Ensemble REST boundary is the intended architecture.
8. Federation (#71) stays parked until the recovery work is complete.
9. SonarCloud (#49) remains separate from recovery merge gating.
10. Runtime artifacts and generated bytecode do not belong in source control.

## Work order

### Phase 0: Baseline

- #100 — Establish and verify the restored baseline.
- Confirm the repository builds/tests from `5c0bd6a`.
- Add only the minimum smoke coverage needed to prove the restored service boundary.
- Phase 0 smoke is limited to behavior already present at `5c0bd6a`; it must not implement Graph, Learning, Memory lifecycle, provider execution, or other Phase 1+ responsibilities.

PR #112 establishes this plan only. Issue #100 remains open until the baseline build/test results and minimal real service-boundary smoke result are recorded.

### Phase 1: Process ownership and installation

- #101 — Define one owner for Graph/Learning/Memory daemon lifecycle.
- #94 — Make process-group startup portable on Windows.
- #95 — Correct Memory Service daemon spawning.
- #96 — Propagate termination signals and prevent orphaned children.
- #97 — Preserve actionable daemon startup diagnostics.
- #102 — Repair installer/systemd template paths and generation.

These are grouped because lifecycle behavior and installation semantics must agree. We should not fix an installer that starts a daemon under the wrong ownership model.

### Phase 2: Canonical REST boundaries

- #103 — Rebuild Graph behind the real Ensemble REST boundary.
- #88 — Wire Learning endpoints through the same boundary.
- #89 — Establish the common Decision Support error envelope.
- #104 — Expose Decision Support through the canonical boundary.

Related issue #90 (graph edge cost data) belongs with the Graph/Learning implementation where the data contract is established.

Phase 2 endpoints must report honest unavailable/not-wired dependency failures rather than placeholder or mocked success.

### Phase 3: Provider execution and arbitration

- #105 — Establish one canonical model-provider abstraction.
- #106 — Replace mocked arbitration with real provider execution.
- #98 — Restore real review/arbitration cost and token accounting.

Provider authentication and execution semantics must be settled before arbitration is declared real.

### Phase 4: Solve, Review, and execution correctness

- #107 — Harden Solve/Review worker contracts, failures, parsing, quorum, and partial results.

This phase must not silently convert unavailable workers or malformed model responses into successful results.

### Phase 5: Learning correctness

- #108 — Make outcome ingestion idempotent and restart-safe.
- #109 — Define scoring and confidence semantics before implementing formulas.
- #91 — Make critical learning failures propagate explicitly.
- #92 — Revisit confidence only after its semantics are defined.
- #93 — Add freshness/sample-size metadata once the underlying data contract is stable.

#92 must not reintroduce unsupported Bayesian terminology. #109 is the specification gate and should be reviewed as a specification before formula implementation.

### Phase 6: System-wide integration and CI

- #110 — Expand CI to exercise the recovered architecture.
- Verify REST routing, Graph, Learning, Decision Support, Solve, Review, provider abstraction, arbitration, installers, and at least one real service-boundary path.
- CI acceptance must enumerate the real boundary paths exercised, not merely require a generic green test job.
- Keep SonarCloud (#49) independent until its external provisioning/configuration problem is resolved.

### Phase 7: Messaging

- #111 — Add explicit subscription filters to Ensemble messaging.

Messaging is implemented after the core service contracts are stable so subscription semantics can be defined against actual event/message contracts rather than guessed interfaces.

### Phase 8: Deferred architecture

- #71 — Service URL routing / transparent remote forwarding / federation.
- #86 — Operational data semantic discovery.
- #1 — Arbiter explanations / neural learning signals.
- Legacy MCP issues #5, #6, #7, #8 remain outside this recovery unless separately reactivated.

#71 is deliberately last.

- #88 -> Phase 2 Learning boundary

- #90 -> Graph/Learning data contract
- #91 -> Phase 5 learning correctness
- #92 -> #109 specification gate
- #93 -> Phase 5 data-quality contract
- #94/#95/#96/#97 -> Phase 1 lifecycle/installation
- #98 -> Phase 3 execution/cost accounting

The recovery issues #100-#111 are the primary tracking surface for the rebuilt implementation.

## Definition of recovered

Claude Ensemble is not considered recovered merely because CI is green.

Recovery requires:

- documented lifecycle ownership;
- deterministic installation;
- coherent REST boundaries;
- real provider execution;
- honest failure semantics;
- durable/idempotent learning;
- defined scoring/confidence semantics;
- integration coverage that exercises the actual architecture;
- no known production mocks or fabricated telemetry;
- all accepted recovery issues resolved;
- only then, federation work begins.
